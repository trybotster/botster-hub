## Scope

- Add a hub-owned worktree record model linked to `SpawnTarget.target_id`; use the spawn target as the admission/root authority rather than inventing another target model.
- Support plain non-git directory targets. A "worktree" is an admitted working directory/reference under or associated with a spawn target; git metadata is optional.
- Add create/list/show/delete worktree semantics. Keep v1 tight; add update only if needed to reconcile status/metadata without awkward delete/recreate behavior.
- Enforce path policy against the associated spawn target:
  - create must reject unknown or disabled target ids;
  - local paths must canonicalize and remain under the target root;
  - traversal, symlink escape, and arbitrary host paths must fail before persistence.
- Persist worktree records inside `HubState` and reload them through `HubRuntime`/`HubDaemon`. On reload, reconcile enough filesystem state to mark missing/stale paths instead of crashing or deleting records.
- Expose daemon/client request and DTO support for list/show/create/delete worktrees, with response projections that trusted same-device clients can consume.
- Update both generated TypeScript daemon protocol artifacts when the Rust daemon protocol changes: `crates/botster-hub-client/generated/daemon-protocol.ts` and `packages/hub-test-support/daemon-protocol.ts`.
- Add `FEATURE_WORKTREES`, register it in the daemon compatibility supported-features list, bump `CONFORMANCE_FIXTURE_REVISION`, and update the support-matrix assertion in `tests/hub_daemon_lifecycle_test.rs`. This follows the spawn-target dependency precedent from commit `97c8942`.
- Document the generic hub worktree boundary and plugin usage: plugins store associations separately and reference returned worktree ids.

## Non-Scope

- Do not add Project Pipelines ticket, run, gate, review, or artifact fields to hub worktree records.
- Do not require git, shell out to git for the normal create/list/show/delete path, or make `.git` presence part of admission.
- Do not create a second spawn target/target registry or duplicate target-root policy in plugin state.
- Do not implement broad workspace management, branch orchestration, UI workbench behavior, cloud sync, or session spawning changes unless a narrow hook is required to prove the CRUD path.
- Do not delete filesystem trees as part of record deletion unless the ticket is later clarified. For v1, deletion should remove the hub record; destructive filesystem removal would need a separate guarded primitive.

## Assumptions And Unknowns

- Assumption: worktree ids should be stable hub ids, either caller-supplied with validation or generated by the hub, similar to spawn target ids.
- Assumption: v1 fields should include `worktree_id`, `target_id`, local path/reference, status, optional git metadata, and small sanitized metadata. Status should distinguish at least usable/present from missing/stale.
- Assumption: create can admit an existing directory under a target root. If v1 also creates directories, it must create only beneath the canonical target root and still pass the same containment check.
- Assumption: git-aware metadata can be opportunistic fields such as branch/head/repository root when detectable, but failure to detect git must not reject a plain directory.
- Assumption: daemon response roots/paths are trusted same-device local paths, like `DaemonSpawnTarget.root`; committed docs and fixtures should use placeholders or temp paths.
- Unknown: whether the CLI needs a `worktrees` command in this ticket. The acceptance text names daemon/client requests and DTOs, not CLI. Add CLI only if existing project convention treats daemon CRUD as requiring operator CLI parity.
- Unknown: whether plugins need a Lua capability table immediately. The ticket says docs should explain plugin references; it does not explicitly require Lua helpers. Prefer daemon/client DTOs first, then add read/validate Lua helpers only if current plugin APIs need them.

## Risks

- Path escape risk: naive string prefix checks can be bypassed by `..`, symlinks, case differences, or trailing separators. Mitigation: canonicalize the target root and worktree path, then use component-aware `Path::starts_with` against the canonical root; keep destructive filesystem deletion out of v1.
- Git regression risk: opportunistic git metadata could accidentally make `.git` required. Mitigation: tests must create and persist a plain directory target with no `.git`.
- Unwired model risk: adding `src/worktrees.rs` without daemon transport/state reload proof would be scaffold only. Mitigation: acceptance tests must drive public `DaemonRequest` calls through a started daemon and restart.
- Authority split risk: Project Pipelines could leak workflow fields into hub records. Mitigation: hub records stay generic; pipeline run/ticket associations remain plugin-owned and reference `worktree_id`.
- Protocol drift risk: Rust DTO changes can desynchronize generated TypeScript. Mitigation: update generator inputs and both checked-in generated artifacts in the same change.
- Reload reconciliation risk: missing paths can cause startup failure if validation is too eager. Mitigation: persisted rows deserialize without touching the filesystem; reconciliation marks status after load.
